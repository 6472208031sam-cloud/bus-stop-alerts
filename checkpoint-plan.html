Option 1: 3 Sequential Checkpoints ✅ SELECTED by Domi 2026-10-17

1. Goal

Detect when a waiting rider's phone transitions to "on the bus and moving toward the next stop" on the AM route only (Bus and St Cecilia), and notify followers via ntfy.

Why AM only: AM is pickup (waiting → boarding). PM is drop-off — the "got off" message already covers it.

2. Checkpoint Design (v2)

Three sequential sub-checkpoints per stop at 50m, 100m, and 150m along the route. The phone must cross them in order.

Sub-checkpointDistance past stopPurpose
A50mBeyond stop-zone shuffling; first proof of movement
B100mSustained movement in route direction
C150mConfirmed — fires "on bus"

Bus: 12 AM stops (excluding final) × 3 = 36 sub-checkpoints.
St Cecilia: 8 AM stops (excluding final) × 3 = 24 sub-checkpoints.
Total: 60 sub-checkpoints, stored as static data per app.

Why sequential, not single: GPS drift is random jitter — it cannot walk 50m → 100m → 150m in the route direction. A bus does exactly that. Strict ordering eliminates drift false-positives entirely.
Why 150m (not 100m): Buses sometimes pull forward 20-30m within the stop zone. 50m spacing keeps the first checkpoint clear of any stop maneuver. Detection is ~6-9 seconds slower than 100m, which is negligible for followers.

3. Detection Logic

// Per-stop progress: 0 = waiting, 1 = hit 50m, 2 = hit 100m, 3 = ON BUS
var checkpointProgress = {};  // stopIdx → 0..3

var cps = AM_CHECKPOINTS;  // AM only (Bus: 36, StC: 24)
for (var i = 0; i < cps.length; i++) {
  var cp = cps[i];           // { stop_idx, seq: 0|1|2, lat, lng }
  var stop = stops[cp.stop_idx];

  // Gate 1: stop must be reached
  // Gate 2: this is the NEXT expected sub-checkpoint in sequence
  if (stop && stop.reached &&
      (checkpointProgress[cp.stop_idx] || 0) === cp.seq) {

    var d = distanceMeters(lat, lng, cp.lat, cp.lng);

    // Gate 3: within 50m of this sub-checkpoint
    // Gate 4: GPS accuracy ≤ 100m
    if (d <= 50 && accuracy <= 100) {
      checkpointProgress[cp.stop_idx] = cp.seq + 1;

      // All three hit in order → ON BUS
      if (cp.seq === 2) {
        var next = stops[cp.stop_idx + 1];
        var msg = "📱 " + deviceId + " on bus, heading to Stop " +
                  next.number + ": " + next.name + ".";  // e.g. "📱 [A82] on bus, heading to Stop 6: ON WHEAT BOOM DR..."
        sendNtfy(msg);
        logEvent('STOP', 'On-bus: ' + msg);
      }
    }
  }
}

4. State Machine

  waiting (0)
    │ phone within 50m of 50m-checkpoint
    ▼
  stage 1 ─── phone within 50m of 100m-checkpoint
    │              (must be AFTER stage 1, strict order)
    ▼
  stage 2 ─── phone within 50m of 150m-checkpoint
    │              (must be AFTER stage 2, strict order)
    ▼
  ON BUS → ntfy sent, no repeat

Out-of-order hits are ignored (e.g., phone near 100m point without hitting 50m first does nothing).

6. ntfy Message

📱 [A82] on bus, heading to Stop 6: ON WHEAT BOOM DR - OPPOSITE 434 WHEAT BOOM DR AT PARK.

Existing 📱 [X##] prefix.

Follower parser required (new): The follower does NOT currently parse "on bus" messages — it would show as "Unrecognized message." Must add a regex pattern for 📱 [X##] on bus, heading to Stop N: Name. to both follower pages (Bus and St Cecilia) before this ships. See v4.5 "off bus. Tracking stopped." parser as template.

7. Follower Behavior on "On Bus"

When the follower receives 📱 [X##] on bus, heading to Stop N: Name:

  1. Parse it — new regex pattern (see §6 warning). Extract device ID and target stop.
  2. Clear the waiting banner for that device — they boarded, so the "Waiting for bus at Stop X" pill must go away. Otherwise it sits stale on the map.
  3. Log it in the event log like other messages.
  4. Do NOT move the bus marker — the marker position comes from "at Stop X" arrival messages. The on-bus message is informational only.
Why not move the marker: "Heading to Stop 6" tells us direction, not position. The next "at Stop 6" arrival will place the marker accurately. Moving it speculatively would be wrong.

9. Tuning Option (Post-Launch)

Start with strict 3-of-3. If real-world tests show misses (e.g., GPS gap skips the 50m point), relax to 2-of-3 (allow skipping one). This is a one-line change.

Option 2: Dwell + Speed + Bearing (no static checkpoints) — NOT SELECTED

O2-1. How It Works

Three gates, no pre-calculated coordinates:

GateCheckThresholdPurpose
1. DwellPhone stationary within stop radius30+ seconds, speed < 3 km/hProves you were waiting, not walking through
2. SpeedPhone moving fast> 15 km/h sustained 5+ secondsProves vehicle, not pedestrian (walk = 3-6 km/h, bus = 20-50 km/h)
3. BearingMovement direction matches routeWithin 45° of route bearing at that pointProves following the route, not a cross street

All three gates pass → 📱 [X##] on bus, heading to Stop N: Name.

O2-2. Detection Logic

// Per-stop state
var busDetect = {};  // stopIdx → { dwelled: bool, dwellStart: timestamp }

onPosition(lat, lng, speed, accuracy):
  for each AM stop s (reached, not final):
    var st = busDetect[s.idx] || { dwelled: false };

    // Gate 1: Dwell — stationary within stop radius for 30s+
    if (!st.dwelled) {
      if (distTo(s) <= s.radius && speed < 0.83) {  // 0.83 m/s = 3 km/h
        if (!st.dwellStart) st.dwellStart = now;
        if (now - st.dwellStart >= 30000) st.dwelled = true;
      } else {
        st.dwellStart = null;  // moved or sped up, reset
      }
    }

    // Gate 2+3: Speed + Bearing (only if dwelled)
    if (st.dwelled && !st.fired) {
      if (speed >= 4.17 && accuracy <= 100) {  // 4.17 m/s = 15 km/h
        var routeBearing = bearingToNextStop(s);  // from route path
        var moveBearing = gpsBearing();            // from consecutive fixes
        if (angleDiff(routeBearing, moveBearing) <= 45) {
          st.fired = true;
          sendNtfy("📱 " + devId + " on bus, heading to Stop " + next.number + ": " + next.name + ".");
        }
      }
    }
    busDetect[s.idx] = st;
